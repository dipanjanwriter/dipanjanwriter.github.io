ClinView Portal Product Guide

Administrator and user guide · Release 1.0 · Document CVP 26.1

This is a writing sample. ClinView Portal is a fictitious product, and all data, names and screens shown here are illustrative. It is written to the structure I use for enterprise module reference guides: overview, installation, configuration, then task-based usage.

Overview

Introduction

ClinView Portal presents a unified view of a patient's clinical documentation by aggregating content from one or more connected repositories into a single browser-based interface. Clinicians can browse, filter, and open documents, diagnostic images, and multimedia content without switching between separate applications.

The product is composed of a small set of cooperating services: a web user interface, a backend-for-frontend (BFF) service that mediates requests between the UI and downstream systems, a content API that retrieves documents and metadata from configured repositories, and a shared configuration store that governs how content is categorized, filtered, and displayed.

  • Consolidated patient record view across connected repositories
  • Configurable categories, filters, and column layouts
  • Native viewing of common document, image, video, and audio formats
  • Support for single sign-on and token-based authentication
  • Optional launch from a third-party electronic health record (EHR) using a standards-based context handoff

Version compatibility

Each release of ClinView Portal is tested against a specific set of supported browser versions, identity provider versions, and companion service versions. Before upgrading any component, confirm that the target versions of the UI, BFF, content API, and configuration services are listed as compatible in the release notes for that version. Deploying mismatched component versions is not supported and may result in missing content, authentication failures, or degraded performance.

ComponentMinimum supported versionNotes

The viewer natively renders the most common clinical document and media formats. Content in an unsupported format can still be listed and downloaded, but is not rendered inline.

Licensing

Use of ClinView Portal requires a valid license issued by the vendor and activated through the license service that ships with the product. The license governs the number of named or concurrent users, the modules enabled (for example, corrections workflows or full-text search), and the license term. Contact your account representative to obtain, renew, or expand a license.

Note: Operating the product with an expired or invalid license may disable content retrieval until a valid license is applied.

Installation

Deployment overview

A typical ClinView Portal deployment consists of four logical tiers: the web UI, the BFF service, the content API, and one or more repository adapters that translate requests into the native protocol of each connected source system. These tiers can be installed on separate hosts for scalability, or combined on fewer hosts for smaller deployments.

Components required for all deployments

  • A relational database instance to host the shared configuration schema
  • An identity provider that supports OpenID Connect or an equivalent token-based protocol
  • A web server capable of hosting the UI, BFF, and API components (IIS or an equivalent supported host)
  • Network connectivity, including any required firewall rules, between each component and the repository systems it queries

Repository adapter components

Depending on which source systems are connected, a deployment may also require one or more repository-specific adapter components. Each adapter translates the product's internal content and metadata model into the query language and authentication scheme used by that repository. Consult the adapter-specific installation notes for the repository types in use at your site.

System requirements

TierMinimum requirement
Web/API server4 CPU cores, 8 GB RAM, current Windows Server LTS release
DatabaseCurrent supported release of the organization's standard RDBMS
Client workstationCurrent evergreen browser, 1366×768 minimum resolution

Secure environment recommendations

To achieve a secure environment:

  1. Terminate all external traffic with TLS 1.2 or later.
  2. Place the BFF and content API behind a load balancer configured for session affinity where required.
  3. Restrict direct network access to the database and repository adapters to the application tier only.
  4. Rotate service account credentials and signing keys on a defined schedule.

Installing the components

Each server-side component ships with both a graphical setup wizard and a silent command-line installer, so that installation can be scripted as part of a standard deployment pipeline. The general installation sequence is:

  1. Provision and initialize the configuration database schema.
  2. Install and configure the configuration service.
  3. Install and configure the content API and any required repository adapters.
  4. Install and configure the BFF service.
  5. Install and configure the web UI.
  6. Configure the identity provider integration for each component.

Note: Install components in the order above. The UI and BFF depend on the content API and configuration service being reachable at first startup.

Command-line installation parameters

The command-line installer for each component accepts a common set of parameters. Typical parameters include the target web site identifier, the application name, the application pool under which the component runs, and the root path of the API it should call.

ParameterDescription
SITE_IDIdentifier of the target web site on the host
APP_NAMEName under which the component is registered
APP_POOLApplication pool used to run the component
API_ROOTBase URL of the API the component should call
REQUIRE_SSLWhether the component should reject non-HTTPS requests

Identity and access management

Each component authenticates using tokens issued by the configured identity provider. Configure a client registration for each component (UI, BFF, content API) with the appropriate scopes, redirect URIs, and token lifetimes. The BFF performs a token exchange on behalf of the UI so that the browser never holds credentials with direct access to the content API.

  • Register a confidential client for the BFF with token-exchange permissions
  • Register a public client for the browser-based UI
  • Configure allowed redirect URIs to match each environment (development, test, production)
  • Configure token lifetimes in line with your organization's session-timeout policy

Single sign-on launch from a third-party system

ClinView Portal supports being launched in context from a third-party clinical system using a standards-based launch handoff (comparable to SMART on FHIR). The launching system initiates an authorization request; the BFF exchanges the resulting token for one scoped to the content API, and the UI opens directly to the referenced patient record.

URL integration

The UI can be embedded or deep-linked from another application by constructing a URL that identifies the patient, and optionally an encounter, category, or specific content item to display on load. Query-string parameters control the initial filter state, whether the patient banner is shown, and whether existing tabs are closed when a new link is opened.

ParameterPurpose
patientIdIdentifies the patient record to open
encounterIdOptionally scopes the view to a single encounter
filterEncodes an initial set of filter criteria as JSON
showBannerShows or hides the patient banner on load
closeExistingCloses previously opened tabs when a new link is launched

Logging

Each service writes structured logs to a configurable location and supports adjustable logging levels (Error, Warning, Information, Debug, Trace) per component. Enable Debug or Trace logging only temporarily when diagnosing an issue, since verbose logging can generate a large volume of data in an active environment.

Troubleshooting

Each service exposes a health-check endpoint that reports its own status and the reachability of the services it depends on. Use these endpoints as the first step when investigating a reported outage or partial content failure.

SymptomLikely causeFirst step
Some content is missing for a patient One connected repository is unreachable or slow Check the content API health endpoint and adapter logs
Content fails to load in the viewer Session or token expired, or unsupported format Refresh the session; confirm the format is supported
Page not found after navigating Deep link references content that has been removed or reclassified Verify the identifiers in the URL against the source repository
Continuous redirect or re-authentication loop Clock skew or misconfigured redirect URI Verify server time synchronization and identity provider client configuration

Configuration

Repository configuration mapping

Because connected repositories may use different internal type systems, the configuration layer defines a set of unified content types and unified note types. Administrators map each repository's native document and note types onto these unified types so that categories, filters, and column layouts behave consistently regardless of which repository a given item came from.

  • Create a unified type to represent a category of content across repositories
  • Map one or more native repository types to each unified type
  • Modify or remove a mapping as repository configurations change

Note: Removing a unified type that is still referenced by an active category or filter will hide the affected content until the mapping is corrected.

Application configuration

Category configuration

Categories group related content in the patient overview, for example "Lab Results" or "Imaging." Administrators can add, modify, reorder, and delete categories, and can control which unified types populate each category.

Content list columns

For each category, administrators can configure which metadata columns appear in the content list, including the display name, whether a column is sortable, and the default sort column and direction. Keyword or metadata fields from the source repository can also be exposed as additional columns.

Filters and date ranges

Filter categories (such as department, encounter, facility, or modality) can be enabled, reordered, and scoped to specific categories of content. Date-range filters can be predefined (for example, "Last 30 Days") or left open for the user to specify a custom range.

General settings

  • Standard date and time display format
  • Enabling full-text search across supported content types
  • Enabling telemetry data collection for usage analytics
  • Cache expiration times for metadata and content
  • Patient-context tracking for integration with other clinical applications

Viewer settings

Default image sizing, the behavior of the embedded image viewer, and any custom headers sent to a downstream viewing component can be configured centrally so that the viewing experience is consistent across the organization.

Corrections workflow

When enabled, the corrections workflow lets a clinician flag a document for review and submit a description of the issue. Submitted corrections are routed to the health information management team responsible for the source repository.

Usage

Getting started

Users typically launch ClinView Portal either directly, through a bookmarked link, or in context from within another clinical application. On launch, the patient overview presents the categories, filters, and content list configured by the administrator.

  • Patient overview layout: categories, filters, and the content list for the active patient
  • Gallery view layout: a thumbnail-based alternative for browsing image-heavy categories

User options

Updating language and theme preferences

  1. Select your user name or avatar in the upper-right corner of the window.
  2. Select User Options.
  3. Under Language, choose the preferred display language from the list.
  4. Under Theme, choose Light or Dark to change the application's color scheme.
  5. Select Save. The interface updates immediately without requiring you to sign in again.

Displaying keyboard shortcuts

  1. Select the Help icon in the toolbar, or press the ? key from the patient overview.
  2. Review the list of available shortcuts grouped by task (navigation, filtering, viewer).
  3. Select anywhere outside the panel, or press Esc, to close it.

Accessing patient information

Categories

The categories pane can be expanded or collapsed to reclaim screen space. Users with the appropriate privilege can also define personal categories that are visible only to them, in addition to the categories configured by an administrator.

Adding a personal category

  1. From the categories pane, select New Content Category.
  2. Enter a name for the category.
  3. Select the unified content types that should populate the category.
  4. Select Save. The new category appears under the Personal heading in the categories pane.

Filtering content

Filters can be applied from the filter bar or from a dedicated filters pane. Date filters support both predefined ranges and custom start and end dates. Applied filters can be removed individually or cleared all at once.

Applying a filter

  1. Select Filters in the toolbar to open the Apply Filters pane.
  2. Select one or more values under each filter category you want to apply (for example, Department or Facility).
  3. Under Date Range, choose a predefined range or select Custom Range and enter a start and end date.
  4. Select Apply. The content list updates to show only items that match the selected criteria, and each active filter appears as a chip in the toolbar.
  5. To remove a single filter, select the × on its chip in the toolbar. To remove all filters at once, reopen the panel and select Clear All.

Viewing content

Selecting an item from the content list opens it in an embedded viewer appropriate to its format. Multiple documents or studies can be opened side by side, and any open viewer can be expanded to full-screen mode for detailed review.

Opening a document or study

To open a document or study:

  1. From the content list, locate the item you want to review.
  2. To open the item, select the row or click its Description link. The item opens in the embedded viewer, which selects an appropriate viewing mode automatically based on the content's format.
  3. To open additional items alongside the current one, hold Ctrl while selecting each additional row and then select Open.
  4. Select the Full Screen icon in the viewer toolbar to expand the viewer. Or, press Esc to return to the previous layout.
  5. Click Back to Patient Record, or close the viewer tab, to return to the content list.

Video and audio playback

Supported audio and video content plays back directly in the browser using standard playback controls, provided the client device meets the codec and browser requirements described in the Overview section.

Previewing diagnostic studies

Diagnostic imaging studies can be previewed using a lightweight study viewer with basic zoom, pan, and series-navigation controls before opening the full imaging viewer for detailed interpretation.

Viewing restricted content

Content marked as restricted (for example, behavioral health or substance-use records subject to additional consent requirements) requires an explicit access justification before it is displayed. Access to a restricted patient record is similarly gated and is logged for audit purposes.

  1. Select the restricted item, which is marked with a lock icon in the content list.
  2. In the access justification dialog, select a reason from the list (for example, Direct Care or Emergency Access).
  3. Select Continue. The access request and the reason provided are recorded in the audit log, and the item opens in the viewer.

Flagging documents for correction

When the corrections workflow is enabled, a user can flag a document directly from the viewer and submit a description of the requested correction for review by health information management staff.

  1. Open the document in the viewer.
  2. Select Flag for Correction in the toolbar.
  3. Select the reason category that best describes the issue (for example, Wrong Patient or Incorrect Date).
  4. Enter a description of the requested correction and click Submit. The document is marked as pending correction in the content list until the request is resolved.

Adding a note to a document

To add a note to a document:

  1. Open the document in the viewer.
  2. Select Add Note in the toolbar. Or, select New Note from the notes list.
  3. Choose the visibility for the note (for example, Visible to Care Team).
  4. Enter the note text.
  5. Click Save Note. The note appears in the notes panel alongside any existing notes on the document.

Full-text search

When enabled, full-text search allows a user to search across the textual content of supported documents for a given patient, subject to the same access restrictions and privileges that govern normal browsing. Search results highlight the matching term within the returned document.

  1. Select the Search field in the toolbar and enter a search term.
  2. Press Enter. The content list filters to show only items containing a match.
  3. Open a matching item to view it with the matching term highlighted in the document.
